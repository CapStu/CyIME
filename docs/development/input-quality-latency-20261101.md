# 中文输入的选词与延迟，2026-11-01

SM-X800 的私人测试版 1.15.37 已抓到长串打字的停顿。先看按键在哪一段变慢，再决定动哪条算法。[#53](https://github.com/Cyletix/CyIME/issues/53) 的报告来自联想 Y700 四代、Android 16、1.15.24、26 键，原机原因仍待确认。

## 一次输入会跑什么

下表描述当前主目录。平板采样测的是已安装的 APK，两者分别记录。

| 路径 | 触发和工作量 | 对选词的影响 |
| --- | --- | --- |

## 平板采样

SM-X800，Android 14，私人包 1.15.37（20261389），横屏，系统设置搜索框，保留现有学习状态和设备配置。设备原有 CyLM 调试属性为 `cylm=1`、`cylm_budget=0`（沿用方案预算）、`cylm_gate=0`、`cylm_guard=0`。软件触摸采样从松手到包含候选的帧完成。快速连续输入允许多个键共用一帧。表中的 35、60 ms 为注入间隔设置。

| 场景 | 完整采样 | P50 | P95 | 最大 | 超过 200 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 九键，点亮后第一组，60 ms | 20/20 | 303 | 406 | 455 | 16 |
| 九键，连续测试，60 ms | 132/132 | 68 | 131 | 156 | 0 |
| 九键，连续测试，35 ms | 132/132 | 102 | 199 | 312 | 6 |
| 26 键，切换后，60 ms | 132/132 | 95 | 165 | 225 | 3 |
| 26 键，连续测试，35 ms | 132/132 | 105 | 197 | 236 | 5 |

第一组是「呢」和「形容不上来」。当次最慢键共 455 ms，其中排队 281 ms。另一键引擎 219 ms，同一后台阶段记录到 456 次主缺页。当次 9 个后台超过 50 ms 的键全部有主缺页且线程 CPU 耗时不到后台墙钟耗时的一半。点亮后没有人为清缓存，未确定是哪个文件的页被读回。

其余四组每组按「呢、还是、形容不上来、形容不上来的一次错序」各打三轮。实测键间隔中位为 42 和 67 ms。九键 35 ms 组最慢键共 312 ms，引擎 14 ms，结果投递后等主线程 215 ms。26 键 35 ms 组最慢键共 236 ms，引擎 42 ms，等主线程 121 ms。可见慢键既有排在引擎前的，也有发生在引擎返回后的。此采样没有记录逐键搜索分支数。

**只改 CyLM 开关做对照。** 在原学习状态、同一编辑框、同一轮 132 个九键输入下按开 → 关 → 开各跑一次。整键 P95 依次为 172、193、198 ms，超过 200 ms 的有 1、5、6 键。关闭那轮最慢 269 ms。关掉 CyLM 仍会出现尖峰，三轮的波动不足以量化该模型本身增加了多少延迟。测试后恢复了原开关和九键布局。

**主线程当时在做什么。** 另用 Perfetto 记录相同九键输入的线程调度及界面帧。日志 132 键完整，环形跟踪里有 27 键可对齐到完整调度区间。一个慢键共 217 ms，引擎 17 ms，从投递候选到主线程接手 156 ms。这段时间主线程运行 65 ms、可中断睡眠 73 ms，有与之重叠的视图遍历 102 ms、绘制 48 ms、窗口重新布局 34 ms。各帧片段有嵌套，不能相加。没有定位到具体哪一个窗口或 Compose 节点。跟踪轮单列，不与关闭跟踪的计时混算。时钟对齐和 SQL 在采样目录的 `inspect_trace.py`，结果在 `main-thread.txt`。

**实际候选。** 停顿后查看同一测试框。两个布局的「还是」「形容不上来」均为首选，「呢」均在第二位。26 键 `xingrongbusahnglai` 展开后前五没有「形容不上来」。全拼九键同样的邻位交换首选「形容不派你来」，横向首栏没有目标。候选图片在采样目录的 `menus-26.png`、`expanded26.png`、`menus-9.png`。工作区的独立引擎验证和已装包的输入表现各自记录。

## 按下按键时，键帽上方的放大字母

平板原设置为开启。在系统设置搜索框、中文 26 键、同一批输入（`nn`、`haishi`、两条一正一错的长串），按开 → 关 → 开测，每组 132 键，35 ms 节奏，20 ms 手势间隔以内的连击另测。三组原始日志均按键位布局、松手和逐键编码长度检查完整。这里的时间是松手到候选帧完成，放大字母本身从按下开始显示。

| 点按放大字母 | 整键 P50 | 整键 P95 | 最大 | 超 200 ms |
| --- | ---: | ---: | ---: | ---: |
| 开，第一轮 | 105 ms | 214 ms | 268 ms | 9/132 |
| 关 | 77 ms | 147 ms | 179 ms | 0/132 |
| 再开 | 116 ms | 224 ms | 242 ms | 11/132 |

现装 1.15.37 在按住 T 时拍到了 T 键正上方的放大字母。在同一系统搜索框切英文、开启气泡，设为按住 20 ms、松手间隔 15 ms，连敲 `nnbbuunn` 后读回的八个字符完全一致。测试结束恢复原开关和九键。

早期键盘在 `drawWithContent` 直接画提示。10 月 18 日的布局提交 `92722b7c` 引入独立气泡窗口，后来 `cf53aae0` 把弹窗设为不接收触摸来修双击。普通点按弹窗仍会做标称 120 ms 的入场动画。工作区目前已将普通点按放回 IME 窗口的绘图层，按下事件直接画满，不接收触摸。此前三星平板隔离界面的旧／新实现对照，完整显现中位数从 139.5 ms 降到两轮 38.5、46.5 ms。该改动未装入平板系统输入法，仍需在新包复跑本表和宿主双击检查。[首帧和连打证据](mobile-feedback-20261101.md#点按首帧和打字期间的窗口开销)

## 以后的判定

1. **每轮先跑冒烟。** 短码、同码词、完整长句和只错一次的对照用例都从正常界面逐键输入。核对目标位置、能否点选并完整上屏、有没有丢键，保留个人词库状态。首轮和连续复打分开。新增的计时检查逐个核对布局、松手事件、编码长度和帧数。采样缺失或清词失败返回 2；任何单键超过指定预算返回 1；只有本次采样完整且在预算内才返回 0。
2. **引擎改动继续走既有九键硬门禁。** 在相同语料、输入协议和词库下，分别跑空学习库、固定的 3000 条学习记录。比较每键候选排名、错误切分、停顿后变化、词典遍历和束搜索工作量，再做同会话的基线与改版交替计时。任一独立用例工作量超限或目标退位都要保留。26 键和 14 键按自己的方案回放；九键门禁不覆盖它们。本轮未用 WSL、未执行全量同源引擎门禁。[固定回归流程](t9-algorithm-regression.md)
3. **对真机尖峰保留独立判定。** 本轮用 200 ms 作为捕捉肉眼可感停顿的冒烟红线，超一次就标出该键。它不是理想延迟，也不替代逐键相对性能门禁。以同机、同词、同设置和同打字节奏比较几个版本。热机和首轮分别报告，不能用平均改善抵消单键卡顿。

在 Windows 上给指定日志做复查，例如：

```powershell
python tools/ime_lab/key_latency_report.py D:/CyIME-Data/eval/input-latency-audit-20261101/26-35.log --layout qwerty --smoke-words ne,haishi,xingrongbushanglai,xingrongbusahnglai --rounds 3 --max-key-ms 200
```

原始采样、逐项候选图片、测试语料及脚本在 `D:/CyIME-Data/eval/input-latency-audit-20261101/`。先查的是主线程迟迟没接到候选更新的时间，以及第一组为什么发生大量主缺页。只有当同一条慢键的搜索计数也升高，才据此缩搜索范围并重验原本能答对的句子。
